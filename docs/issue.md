## Issue #1 服务契约与数据归属设计

**标签**：`设计`

### 要做什么

写出订单提交、预留库存、记录查询的请求与响应；
解释 400 / 404 / 409 / 502 各自的语义和数据归属。

### 结论

| 状态码 | 语义 | 谁的问题 |
| --- | --- | --- |
| 200 | 成功（含幂等命中，用 `chongfu` 区分） | — |
| 400 | 请求形状/参数不对 | 调用方 |
| 404 | 商品或记录不存在 | 调用方 |
| 409 | 业务冲突（缺货 / 编号内容冲突 / 超规则上限） | 调用方 |
| 502 | 依赖失败 | 服务方 |

**数据归属**：
- 商品、库存、预留记录 → **库存服务**
- 编排、错误分类、页面 → **Node-RED**
- Node-RED **不得**直接读 `kucun.db`

### 验收条件

- [x] 正常与错误示例都有可验证的用例
- [x] 每个状态码在 `tests/test_api.py` 有断言
- [x] 有静态检查确保编排层没直连数据库

## Issue #3 独立库存服务与事务

**标签**：`核心功能`

### 要做什么

用 FastAPI + SQLite 实现商品查询、库存预留、记录查询。
**库存减少与预留记录写入必须在同一事务完成。**

### 关键实现

```python
lian.execute("BEGIN IMMEDIATE")
# ① 幂等检查  ② 商品存在性  ③ 库存检查
# ④ 条件更新（WHERE kucun >= ?）+ 检查 rowcount
# ⑤ 插入预留记录（request_id 是主键）
lian.execute("COMMIT")
```

- `request_id` 设**唯一约束**（主键）
- ④ 的 `rowcount != 1` 必须回滚，**绝不能返回成功**
- SQLite 开 WAL + `busy_timeout`，缩短事务、不在事务内做网络等待

### 验收条件

- [x] 同一编号不重复扣减
- [x] 编号冲突可识别（内容不同 → 409）
- [x] 并发下不超卖、不出现负库存
- [x] 重启后记录保留

## Issue #4 编排主链路与错误分类

**标签**：`核心功能`

### 要做什么

接通正常与失败分支，保存各阶段消息结构的脱敏示例，
从页面请求能一路追踪到库存结果。

### 分支设计

```
POST /api/orders
  ├─ Function 形状校验（2 路输出）
  │    ├─ 合法 → HTTP Request → Function 按状态码分类 → 200/409/404/400/502
  │    └─ 非法 → 400
  └─ Catch（网络错误/超时）→ 502 + "结果未知，先查编号"
```

### 验收条件

- [x] 每个 Function 都保留 `msg.req` / `msg.res`（有静态测试）
- [x] 每个 `http in` 都能走到 `http response`（有可达性测试）
- [x] 5xx 与业务拒绝分开处理
- [x] 超时文案引导用户"先查再重试"

## Issue #5 用户操作页面

**标签**：`界面`

### 要做什么

独立实现表单、列表、筛选、详情与错误反馈。页面读**真实接口**，
提交中防重复点击。

### 设计要点

- 用 `httpStatic` 提供，与 API **同源**，避免 CORS
- 库存只显示服务端返回的值，**页面不做任何本地扣减**
  （页面自己算库存，一刷新就露馅）
- 所有接口文本过 `zhuanYi()`，不拼 `innerHTML`
- 按钮禁用只是体验优化；**幂等靠服务端**

## Issue #6 幂等与异常策略

**标签**：`核心功能` `一致性`

### 要做的判断

| 问题 | 结论 |
| --- | --- |
| 同编号同内容 | 返回原结果，标记 `chongfu`，不扣减 |
| 同编号不同内容 | 409 冲突 |
| 依赖不可用 | 返回 5xx，**绝不返回成功** |
| 超时 | 结果未知，先查编号再决定 |
| 要不要自动重试 | **不自动重试**。只给人工重试指引 |

### 为什么不做自动重试

指导书说"仅在库存服务通过幂等测试后，才可增加最多 2 次带间隔的重试"。
幂等测试是通过了，但自动重试会掩盖真实问题（比如依赖在持续抖动），
而且在课程演示里反而看不出超时的正确行为。所以这次选择了保守做法。

### 验收条件

- [x] 幂等 + 冲突 + 并发边界都有自动测试
- [x] 超时文案明确说"结果未知"
- [x] 被规则拒绝的请求不动库存

## Issue #7 自主扩展：领用上限规则与规则版本

**标签**：`自主功能`

### 用户问题

管理员要按商品类别设领用上限，并且**规则改过之后要能说清历史记录是按哪一版批的**。

### 上游有什么 vs 本人新增什么

| 能力 | 谁提供 |
| --- | --- |
| 消息路由、HTTP 节点、错误捕获 | 上游 Node-RED |
| 业务规则、版本管理、累计统计 | **本人实现**（`service/kucun.py`） |

### 规则

- `danci_zuida`：单次上限
- `meilei_zuida`：同一商品累计成功领用上限
- `banben`：版本号，每笔预留记录保存 `guize_banben`

### 验收条件

- [x] 修改上限后，同一商品两种数量能证明规则真实生效
- [x] 规则校验在扣减**之前**（被拒的请求不动库存）
- [x] 每笔记录都带当时的规则版本
- [x] 没有规则时明确返回"未做上限校验"，不假装有规则
- [x] 禁止把用户输入交给 `eval` 或系统命令（本服务无任何此类调用）

### 踩到的坑

规则生效时间戳一开始只精确到秒，导致同秒内建的两个版本排序不确定，
**刚存的 v4 没生效**。被自动化测试抓到（库存被扣了但本该被拒）。
改成微秒精度后解决。
