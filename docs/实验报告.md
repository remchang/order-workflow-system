## 一、需求分析

### 1.1 要解决的问题

物资领用这种"轻流程"通常散落在聊天记录和 Excel 里，带来三个具体麻烦：

| 编号 | 问题 | 后果 |
| --- | --- | --- |
| P1 | 网络慢时申请人不小心点了两次 | **库存被扣两次**，且事后很难发现 |
| P2 | 请求超时了，不知道该不该重试 | 不敢重试（怕重复扣）或乱重试（真重复扣了） |
| P3 | 规则改过了 | 事后没人说清"当时是按哪条上限批的" |

### 1.2 需求拆解

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| R1 | 两个进程独立运行，各有健康检查 | `/health` 各自可访问 |
| R2 | 页面填写编号/商品/数量，提交得到明确结果 | 操作页面 |
| R3 | 工作流校验后**通过 HTTP** 调库存服务 | 流程里没有直连数据库 |
| R4 | 正常、非法输入、库存不足、依赖错误走不同分支 | 6 条演示用例全对 |
| R5 | 可按编号查询已完成记录 | `/api/orders/{编号}` |
| R6 | 至少 10 种商品，含充足/低库存/零库存 | 种子数据 11 种 |
| R7 | SQLite 持久化，重启后记录保留 | `test_shuju_ku_zhongqi_hou_jilu_hai_zai` |
| R8 | 同编号不重复扣减，内容冲突可识别 | 幂等测试 |
| R9 | 并发边界不产生负库存 | 并发测试 |
| R10 | 区分业务拒绝 / HTTP 5xx / 网络异常 | 流程按状态码分类 + Catch |
| R11 | 一项自主扩展，真实影响业务结果 | 领用上限规则 + 规则版本 |

### 1.3 非目标

- 不做认证与权限。课程单机环境，写了也没法验证有效；
  已在"已知限制"里明确列为上线前必须补的项。
- 不做自动重试。指导书说"仅在库存服务通过幂等测试后才可加最多 2 次重试"——

- 不接任何真实支付、短信或生产系统。

## 二、架构与设计决策

### 2.1 两个进程，一条 HTTP 契约

```
用户浏览器
   │  POST /api/orders（同源，不跨域）
   ▼
Node-RED :1880  ── 形状校验 → 分支 → HTTP Request ──┐
   ▲                                                │
   └──────── HTTP Response ◄── 按状态码分类 ◄────────┤
                                                    ▼
                              库存服务 :8001 ── 规则校验 → SQLite 事务
                                                    │
                                                    ▼
                                            data/kucun.db
```

### 2.2 决策一：数据所有权必须划清

**Node-RED 不许碰 `kucun.db`。** 有一条测试
`test_meiyou_jiedian_zhijie_du_sqlite` 静态检查所有 Function 代码和 URL，
确保没有出现 `kucun.db` 或 `sqlite`。

理由：一旦编排层直接读库，"数据归谁"就没了。
以后库存服务换实现、加缓存、做读写分离，编排层都得跟着改。
而通过 HTTP 契约调用，编排层完全不知道后面是什么实现。

**代价**：多一次网络调用，多一个故障点。
**收益**：可替换性。对本实验的教学目的来说，收益远大于代价。

### 2.3 决策二：幂等 = 编号 + 内容双绑定

```python
jiu = 查 request_id
if jiu is not None:
    if jiu["neirong_zhiwen"] != zhiwen:   # sku|quantity 的稳定指纹
        raise 409  # 同号不同内容
    return "chongfu", jiu                  # 同号同内容 → 幂等命中
```

只按编号去重是不够的：调用方改了数量再提交，
会被静默当成"重复请求"返回成功，但数据完全没动。
**这是最危险的假成功**——日志显示成功，数据对不上，事后极难发现。

### 2.4 决策三：不超卖靠"条件更新 + 检查受影响行数"

```sql
UPDATE products SET kucun = kucun - ? WHERE sku = ? AND kucun >= ?
```

```python
if you.rowcount != 1:
    lian.execute("ROLLBACK")
    raise KucunCuowu(409, "库存刚刚被其他请求占用，请重试")
```

如果把"库存够不够"用一次单独的 `SELECT` 判断，
两条并发请求会**都读到"够"**，然后都去扣 —— 就超卖了。

把条件写进 `WHERE` 让数据库自己做原子判断，
`rowcount != 1` 说明被抢先了，**必须回滚并返回失败**。

指导书特别强调："更新受影响行数为 0 时不得仍返回成功。"
这句话就是这个意思。

`test_bingfa_bu_chaomai` 用两个线程同时申请库存只够一条的商品，
断言**恰好一条成功、库存不为负**。

### 2.5 决策四：业务拒绝 ≠ 依赖故障

| 状态码 | 类型 | 处理 |
| --- | --- | --- |
| 2xx | 成功 | — |
| 409 | 业务拒绝 | 改输入，**同一编号可重用** |
| 404 | 商品不存在 | 改商品 |
| 400 | 请求问题 | 改请求 |
| 5xx → **502** | 依赖失败 | 别急着重试，先查编号 |

前端也按这个分类给不同提示（见 `orders.js` 的 `xianshiCuowu`）。

为什么不能一律 200 或一律 500：
业务拒绝是"你的问题，改输入再来"，依赖故障是"我的问题，等等再试"。
调用方的决策完全不同。

### 2.6 决策五：超时 ≠ 失败

Node-RED 的 `Catch` 节点捕获网络错误后，**不返回"失败"**，而是：

```javascript
msg.payload = {
    ok: false,
    lei_xing: "wangluo_yichang",
    xiaoxi: "调用库存服务失败：" + cuo,
    jiaoyi: "结果未知。请先用同一个编号查 GET /api/orders/{编号} 确认是否已经扣减，"
          + "再决定要不要重试。不要直接重复提交。"
};
```

有一条测试 `test_chaoshi_bu_bei_dangcheng_shibai` 检查这段文案里
必须出现"未知"或"查"字——**防止以后有人把它改成简单的"失败了"**。

### 2.7 决策六：自主功能——领用上限规则 + 版本记录

上游 Node-RED 没有业务规则概念，FastAPI 也不是库存成品。
这一块完全是自己设计的：

| 规则 | 字段 | 说明 |
| --- | --- | --- |
| 单次上限 | `danci_zuida` | 一次申请不能超过 N 件 |
| 单类累计上限 | `meilei_zuida` | 同一商品历史成功领用总和不能超过 M |
| 规则版本 | `banben` | 每次修改产生新版本 |

**每笔预留记录都保存 `guize_banben`**。为什么：

> 规则改过之后，事后审计必须能回答"这笔申请当时是按哪一版批的"。
> 没有版本号，历史记录就失去了可解释性。

规则校验**放在库存扣减之前**。被规则拒掉的请求绝不能动库存——
`test_guize_jujue_bu_dong_kucun` 拿扣减前后的库存做对比来证明这一点。

#### 这里踩了一个真实的坑

第一版规则用 `time.strftime("%Y-%m-%dT%H:%M:%S")` 记生效时间（秒级精度）。
结果：同一个秒内建的两个版本时间戳完全相同，
`ORDER BY shengxiao_shijian DESC LIMIT 1` 退化成任意顺序，
**刚存的 v4 没生效，用的还是启动时的 v1**，被规则拒绝的请求照样扣了库存。

测试 `test_guize_jujue_bu_dong_kucun` 直接把这个 bug 抓出来了
（断言 `51 == 60` 失败，说明库存被扣了 9）。

修法：时间戳改用微秒精度的 ISO 格式（`isoformat(timespec="microseconds")`），
字符串排序就等于时间排序。

**这个 bug 值得记下来**：秒级时间戳做排序键，是一类很典型的、
"测试跑得快才会暴露"的问题。

### 3.4 编排层的测试方式（以及为什么这样写）

本机**没有跑 Node-RED**（`npm install node-red` 要下约 80MB，
本机网络实测约 100 KB/s，会浪费大量时间）。

所以 `tests/test_flows.py` 把流程 JSON **当数据**来验证：

| 检查 | 抓什么错 |
| --- | --- |
| 连线目标是否都存在 | 悬空连线（Deploy 会出错） |
| Function 输出路数 vs 接线组数 | 声明 2 路只接 1 组（消息会丢） |
| 入口 → 响应节点的可达性遍历 | 请求挂住不返回 |
| 有没有 `return {` 新对象 | 丢 `msg.req`/`msg.res`（指导书点名的坑） |
| 有没有 Catch 且后面接了响应 | 网络异常时挂住 |
| 超时文案是否含"未知/查" | 把超时当失败 |
| 有没有直连 SQLite | 破坏数据所有权边界 |
| `/health` 是否依赖外部服务 | 排障分不清谁挂了 |

**这不能替代端到端运行**，但它确实能抓到上面这些真实会犯的错。
未实跑的部分写在"已知限制"里，**没有写成实测通过**。

## 四、问题与反思

### 4.1 最有价值的收获：区分"失败"和"不知道"

一开始我写的错误处理是"调不通就返回失败，让用户重试"。
想清楚之后才发现这里有陷阱：

> 超时只说明"我没等到回包"，**不代表"对方没执行"**。
> 对方可能已经扣了库存，只是回包在路上丢了。

这时如果返回"失败"让用户重试，就会**重复扣减**。
所以正确的做法是先按编号查，确认没执行再重试。

这个思路和幂等其实是同一件事的两面：
幂等解决"重复提交怎么办"，查询接口解决"不知道成没成怎么办"。

### 4.2 关于"防重复点击"的认知修正

页面上禁用按钮是**体验优化**，不是幂等保证。
先 curl 一下照样能重复提交。
真正的保证只能是服务端的**唯一约束 + 事务**。

这条写在 `orders.js` 的注释里了，避免以后有人以为前端挡住了就够了。

### 4.3 秒级时间戳的教训

前面讲过那个规则版本排序的 bug。补充一点反思：

它属于"测试跑得快才会暴露"的问题。
手测时人点两下至少隔几秒，永远不会碰到；
只有自动化测试在同一个秒内连续建两个版本才会暴露。

**结论：自动化测试不只是回归保护，它还会跑到人手速到不了的状态。**

### 4.4 还没解决的问题

1. **分布式一致性**。本实验用 SQLite 单机事务 + 进程内锁。
   多实例部署时进程内锁失效，SQLite 也不适合多写。
   真要上多实例，得换 PostgreSQL + 唯一约束 + 队列。
   指导书也说了"这不等同于已解决分布式事务"。
2. **没有认证**。1880 端口只绑回环，但开放访问前必须加认证。
3. **没有自动重试**。只给了人工重试指引。
4. **编排层未端到端自动化**。这是本次最明显的缺口。

## 五、思考题

**1. Function 节点与独立业务服务分别适合承载什么逻辑？**

Function 适合**无状态、单条消息内**的逻辑：字段改名、形状校验、
路由分支、拼 URL。它的状态只有内存/文件 Context（非事务），
没法保证并发安全。

独立服务适合**有状态、要原子性**的逻辑：事务、幂等、唯一约束、
跨请求的累计统计。而且能被 pytest 直接测，不用起 Node-RED。

判断标准很简单：**这件事做错了会不会导致数据不一致？**
会，就放服务里。

**2. HTTP 503、网络超时与业务缺货为什么应区别处理？**

| | 谁的问题 | 执行了吗 | 应对 |
| --- | --- | --- | --- |
| 业务缺货 409 | 请求方 | 明确没执行 | 改数量，同编号可重用 |
| 依赖 503 | 服务方 | 明确没执行 | 等恢复再试 |
| 网络超时 | 不知道 | **不知道** | 先按编号查 |

前两者可以确定"没执行"，所以能安全重试；
第三者不能确定，直接重试就可能重复扣减。

**3. 唯一请求编号为何还要与请求内容绑定？**

因为只按编号去重会产生**假成功**：调用方改了数量再提交，
系统认为"这个编号见过了"，返回成功，但数据完全没动。
调用方拿到 200 以为处理了，实际库存没变。

绑定内容后，这种"同号不同内容"返回 409 冲突，
调用方立刻知道要和之前那次对齐。

**4. 文件 Context、SQLite 事务与分布式事务分别保证什么？**

- **文件 Context**：跨进程重启大致能读到（有刷盘窗口）。
  保证不了事务、唯一约束、并发原子更新。只能存参考信息。
- **SQLite 事务**：单机 ACID、唯一约束、
  `UPDATE ... WHERE kucun >= ?` 这种条件更新的原子性。
- **分布式事务**：跨服务/跨库的一致性（2PC、Saga、TCC）。
  代价是复杂度、延迟和可用性都显著下降。

本实验用第二档，**只保证单机**。

**5. 怎样证明流程修改没有破坏既有业务，而不仅是连线变化？**

三层：

1. **契约测试**（22 条）固定了库存服务的状态码和字段名。
   编排层依赖的契约没变，这层就不会破。
2. **流程静态验证**（14 条）盯连线、输出路数、`msg.res`、
   入口可达性。改连线改坏了会被抓到。
3. **端到端演示脚本**（7 条用例）覆盖正常/缺货/非法/不存在/幂等，
   改完流程跑一遍，结果对得上才算没破坏。

**缺口**：没有真正的端到端自动化（Node-RED 没在 CI 里跑起来）。
这写在已知限制里了。
